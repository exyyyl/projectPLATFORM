# План кэширования backend

> Статус: Redis в проекте ещё не подключён. Задача запланирована ближе к
> production после завершения основных учебных сценариев.

Кэширование сейчас не является обязательным: сначала нужны реальные замеры
нагрузки и медленных запросов. Prisma/PostgreSQL и индексы достаточно быстры для
текущего этапа, а преждевременный кэш усложнит права доступа и инвалидирование.

## Что можно кэшировать позднее

- справочники дисциплин и групп tenant — TTL 30–120 секунд;
- опубликованные новости — TTL 30–60 секунд;
- агрегированный `/academic/overview` — короткий TTL 15–30 секунд;
- тяжёлую агрегированную статистику прогресса — TTL 10–30 секунд.

Ключ обязан включать контекст доступа, например:

```text
academic-overview:{tenantId}:{role}:{userId}
published-news:{tenantId}:{role}:{page}:{filtersHash}
course-progress:{tenantId}:{courseId}:{courseGroupId}
```

Нельзя использовать общий ключ `courses` или `overview`: так данные одного
пользователя/tenant могут попасть другому.

## Что не кэшируем сейчас

- проверку `isActive` пользователя и tenant в JWT strategy;
- refresh tokens и операции их ротации;
- проверки владения перед записью;
- персональные уведомления без строгого user-scoped ключа.

Проверка активности — один indexed lookup по primary key на запрос. Для текущей
нагрузки безопасность важнее экономии этого запроса. Если нагрузка станет
существенной, можно перейти на Redis/session version, но тогда нужно явно
определить допустимую задержку принудительного logout.

## Реализация при необходимости

1. Снять метрики p95/p99 и определить действительно медленные endpoint.
2. Подключить Redis как общий кэш всех backend-инстансов.
3. Использовать cache-aside: чтение из Redis → при промахе PostgreSQL → запись с
   TTL.
4. После create/update/delete удалять связанные ключи; TTL остаётся страховкой.
5. Тестировать отсутствие утечки между user/role/tenant и корректность
   инвалидирования.

## Приоритет использования Redis перед production

1. Общее хранилище строгого rate limit для auth на нескольких backend-инстансах.
2. Очередь фоновых задач для выпусков материалов и уведомлений по расписанию
   (например, BullMQ).
3. Кэш только тех чтений, для которых метрики подтвердили пользу.

Redis не станет основной базой: пользователи, курсы, оценки и история остаются
в PostgreSQL. Потеря кэша не должна приводить к потере учебных данных.

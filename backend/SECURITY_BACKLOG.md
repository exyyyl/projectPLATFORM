# Security backlog и обязательный pre-production gate

Этот файл содержит отложенные решения, которые нельзя потерять между этапами
разработки. Раздел **«Обязательно перед production»** является блокирующим
чек-листом выпуска, а не необязательным списком улучшений.

## Принятые решения

- `admin` работает и в dashboard, и в основной платформе. На платформе он видит
  все дисциплины, назначения, группы, курсы и прогресс своего tenant и может
  контролировать учебный процесс. Dashboard — отдельный интерфейс управления,
  а не отдельная урезанная учётная запись.
- `superadmin` предназначен для управления всеми tenant. Он не создаётся
  demo-seeder и добавляется одноразовой CLI-командой из `SUPERADMIN.md`.
- Access JWT дополнительно сверяется с БД на каждом защищённом запросе. Отключение
  пользователя или tenant немедленно приводит к `401`; frontend должен очистить
  локальную авторизацию.
- Production CORS работает только по явному allowlist из `CORS_ORIGIN`.

## Отложено: полноценная multi-tenant авторизация

Сейчас вход ищет пользователя по email, а аккаунт содержит обязательный
`tenantId`. Перед подключением нескольких реальных организаций необходимо:

1. Определять tenant по доверенному host/subdomain, а не принимать `tenantId`
   из body запроса.
2. Выполнять вход по составному ключу `(tenantId, normalizedEmail)`.
3. Отделить глобальную идентичность суперадминистратора от tenant-пользователей
   либо формально определить его home tenant.
4. Добавить защиту от подмены `Host` за reverse proxy и разрешить только
   известные домены.
5. Расширить security-тесты сценариями с несколькими tenant для каждого нового
   учебного модуля.

Ближе к завершению admin dashboard суперадминистратор должен получить отдельную
операцию «войти в контекст tenant». Backend выдаёт короткоживущий контекст,
содержащий реального actor и выбранный tenant, а каждое такое действие пишет в
audit log. Передавать произвольный `tenantId` в обычных CRUD-запросах нельзя:
это создаёт риск IDOR и случайной работы не в той организации.

Это решение намеренно лежит «в долгом ящике», пока не начинается подключение
второго реального tenant, но должно быть выполнено до такого подключения.

## Отложено: безопасный rich text / Markdown

Новости создаёт только администратор, но сохранённый Markdown всё равно считается
недоверенным вводом. Перед отображением rich text необходимо отключить raw HTML
либо очищать итоговый HTML allowlist-санитайзером. Frontend не должен передавать
неочищенный текст в `dangerouslySetInnerHTML`.

## ОБЯЗАТЕЛЬНО перед production

- [ ] Перед релизом снова обновить npm-зависимости, выполнить `npm audit`,
      проверить changelog NestJS/Prisma и повторно прогнать все тесты. На
      2026-08-10 точечно обновлены Nest/Prisma, уязвимый Multer устранён;
      `npm audit --omit=dev` показывает 0 production advisories. В полном
      dev-графе остаются advisories инструментов сборки, их проверить повторно.
- [ ] Сделать отдельный строгий rate limit для login/admin login/refresh,
      рассчитанный на несколько инстансов и общее Redis-хранилище.
- [ ] Убедиться, что demo-seed не запускался в production и отсутствуют аккаунты
      с demo-паролями.
- [ ] Включить MFA как минимум для `admin` и `superadmin`.
- [ ] Закрыть или отдельно защитить Swagger в production.
- [ ] Реализовать очистку Markdown/HTML и проверить stored XSS.
- [ ] Провести полный набор tenant/ownership/IDOR тестов для users, groups,
      courses, assignments, submissions, grades, files и notifications.
- [ ] Добавить audit log для административных и superadmin-операций.
- [ ] Проверить HTTPS, cookie-флаги, CORS allowlist, реальные JWT secrets,
      backup/restore и процедуру отзыва сессий.

## Напоминание владельцу проекта

Нельзя считать backend законченным или выпускать его в production, пока два
явно запрошенных пункта не подтверждены отдельно:

1. **Все зависимости обновлены и повторно проверены аудитом.**
2. **Для auth установлены строгие production rate limits.**
